# Passing Tests Is Not Enough

Replication package for the study:

**Passing Tests Is Not Enough: Joint Quality and Security Risk Profiling of AI-Generated Software Changes**

Research theme: **Beyond Functional Correctness**

## Goal

This project studies residual software-quality and security risk after AI-generated software changes satisfy functional tests.

The workflow is deliberately empirical-first:

1. collect public benchmark artifacts;
2. isolate functionally successful changes;
3. measure change shape and source-code quality before/after the patch;
4. analyze residual security evidence in public security datasets;
5. test which inexpensive signals are associated with residual risk;
6. derive a risk-profiling or adaptive-verification policy only if the data support it.


## Current public cohorts

### Repository-level quality cohort

The default configuration uses a public SWE-bench Verified run with complete generated patches and benchmark verdicts:

- model run: `SWE-bench/20260901_mini-v2.4.2_gemini-3-5-flash`
- benchmark: SWE-bench Verified
- generated-patch artifact: `all_preds.jsonl`
- functional verdicts: SWE-bench experiment results

The collector is generic. Other public SWE-bench runs can be substituted in `configs/experiment.yaml`.

### Security cohort

SecurityEval provides Python code generated by GitHub Copilot and InCoder together with manual vulnerability labels and CodeQL/Bandit results.

The security analysis is a **secondary analysis of published artifacts**. It does not claim that this repository reran the original models.

## Quality measurements

The Python-first quality pipeline calculates, where available:

- cyclomatic complexity
- cognitive complexity
- Maintainability Index
- Halstead volume
- maximum AST nesting depth
- function count
- mean and maximum function length
- import count
- Ruff finding counts
- changed files
- changed hunks
- added/deleted lines
- test-file touches
- security-sensitive API additions

Java-specific OO metrics such as LCOM, CBO, RFC, and DIT are intentionally not required for the Python-first main cohort.

## Important interpretation rule

A test-passing patch is not automatically labeled unsafe or low quality.

The repository first records observable measurements. Any composite risk score, quality-regression threshold, or adaptive-verification rule must be derived and validated from data rather than chosen to force a desired conclusion.

## Setup

Python 3.11+ is recommended.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

On macOS, Git must be available on the command line. The quality extraction stage clones public GitHub repositories into a local cache and checks out the exact SWE-bench base commits.

## Run

### 1. Collect public artifacts

```bash
python scripts/collect_swebench.py
python scripts/collect_securityeval.py
```

### 2. Build patch-level measurements

```bash
python scripts/extract_patch_metrics.py
```

### 3. Extract before/after Python quality measurements

Start with a small smoke test:

```bash
python scripts/extract_quality_metrics.py --only-resolved --limit 10
```

Then run the full functionally successful cohort:

```bash
python scripts/extract_quality_metrics.py --only-resolved
```

### 4. Analyze SecurityEval

```bash
python scripts/analyze_securityeval.py
```

### 5. Run statistical analyses and generate initial tables/figures

```bash
python scripts/statistical_analysis.py
python scripts/generate_figures.py
```

Or run the non-expensive stages together:

```bash
python scripts/run_pipeline.py --skip-quality
```

The repository never invokes a paid model API.

## Outputs

Generated data are written under:

```text
data/processed/
results/tables/
results/statistics/
results/figures/
```

Raw public benchmark downloads are excluded from Git by default so the repository stays small and provenance remains explicit.
